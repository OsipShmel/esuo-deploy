# ЕСУО — согласованный план Дней 0–1

Дата: 17 сентября 2026. Роль пользователя: разработчик A. Архитектурная основа — `ESUO-design-doc.md`, с учётом раздела 23. Старый короткий план заменён: строгие тиры и WebSocket больше не являются контрактами.

## День 0 — основа

- Согласовать структуру монорепозитория: инфраструктура, фронтенд, Python и Maven-корень `java-backend`.
- Сохранить Java 21 / Spring Boot 3.5.16; создать `node-app`, `center-app`, оставить `common-dto`.
- Подготовить Flyway-миграцию полной схемы отделения, индексов и ограничений.
- Подготовить PostgreSQL, NATS hub/leaf и приложения с health-check в Compose; пароли вынести в `.env`.
- Развести domain, application, persistence, api, config, messaging; зафиксировать границу A/B.
- Исправить противоречия слотов, идемпотентности, приоритетов, позднего check-in, возврата и REST-маршрутов.

## День 1 — ядро создания талонов (A)

- Доменные модели и JDBC-репозитории отделений, услуг, окон, сотрудников и талонов.
- Единый `IssueTicket` для appointment, QR и walk-in. Appointment создаётся как `booked`, остальные как `waiting`.
- Идемпотентность по `(scope, key)`, проверка хеша, повтор сохранённого ответа; отдельная защита `mp_appointment_id` для внутреннего входа.
- Атомарные счётчики номеров и защита вместимости слота.
- Запрос головы допущенной очереди по `(due_at, seq)` с `FOR UPDATE SKIP LOCKED`, вызываемый только из транзакции будущего Queue Engine.
- Состояние талона, отмена и атомарная запись событий/outbox.
- Минимальные REST-входы для ручной проверки создания и чтения; это вспомогательная интеграция, не полное выполнение зоны B.
- Сборка и ручная проверка запуска без написания тестов.

## Граница с B

B получает публичные Java-команды и DTO из `common-dto`, а также application-сервис A. B отвечает за JWT, окончательные REST/SSE, OpenAPI, публикацию outbox, NATS/RPC, центр, уведомления и интерфейсы. Текущий секрет операторского демо-входа заменяется JWT без изменения ядра.

## Следующие дни

День 2: open/close/call-next, EDF, UniformScoringStrategy, переходы обслуживания и перенаправление.
День 3: check-in, откладывание, таймеры, ETA, запросы уведомлений, восстановление после рестарта.
День 4: конфигурация центра, локальные переопределения, аналитика и админка.
Дни 5–6: эвристика и генератор нагрузки при наличии времени, интеграционные прогоны, документация и демо.

Не добавлять автотесты без изменения текущего указания пользователя. Полнота MVP оценивается отдельно от завершения Дней 0–1.


## Уточнение границы A/B

По указанию пользователя дальнейшая работа ограничена частью A: домен, application-сервисы, JDBC, миграции, конфигурация ядра, алгоритм и аналитика отделения по плану. Пакеты написанного в этой работе кода и Maven groupId — `com.dogma`. Исходная заглушка `OrderCreatedEvent` из репозитория сохраняет свой прежний пакет; она не относится к ядру очереди.

Минимальные REST-контроллеры, обработчик HTTP-ошибок и фильтр request-id были добавлены сверх части A для ручной проверки. Они остаются временным адаптером в пакете `api`, не развиваются и не считаются реализацией задач B. Их дальнейшее оформление и замена — ответственность B. Каркас центра также не развивается в рамках A.

Проект переведён с Spring Boot 4 на 3.5.16: заменены стартеры Web/Flyway и адаптирована сериализация под Jackson 2. Доменная логика и миграции не изменены. Новые тесты не добавляются.
