## 1. Коротко

Центр видит не только очередь отделения, но и здоровье его ПК и приложения — без SSH на отделение и без отдельного
агента мониторинга. Всё едет по тому же NATS, что и события.

- **Важные логи** (WARN, ERROR, жизненный цикл) отделение отправляет само и без потерь: при обрыве связи они ждут на
  диске отделения и доезжают со своим временем. ERROR с отделения виден в Grafana за 8 с.
- **Полные логи** любого уровня центр забирает только по запросу — кнопка «Подробные логи (30 мин)».
- **Метрики сервера** приходят в каждом heartbeat; центр хранит историю 48 ч и строит по ней графики и правила.
- **Правила** превращают метрики в понятные аномалии: «ПК отделения не справляется: CPU 97% уже 1 мин».
- **Снимок диагностики** по кнопке за доли секунды показывает потоки JVM, запросы и блокировки БД, пул соединений,
  связь — и приходит даже при зависшей базе.
- **Зависшая база ≠ нет связи**: центр различает «нет связи» и «данные очереди не обновляются».
- **Хаос-сценарий** ломает CPU, базу, приложение и связь и проверяет, что центр видит, что именно сломалось.

## 2. Закрытый API центра

Новые API отдают логи и внутренности отделений, поэтому первым делом центр закрыт по умолчанию: без входа доступен
только явный список (шлюз клиента, вебхук МП с HMAC, вход, health, документация API, статика). Всё остальное под
`/api/**` и `/actuator/**` — JWT с ролью `NETWORK_ADMIN` (`iss=esuo-center`, токен ноды центр не принимает). Новый
эндпоинт без правки списка автоматически закрыт; `EndpointCoverageIT` проверяет, что каждый обработчик либо в
публичном списке, либо отвечает 401. Учётная запись оператора сети — из `.env` (`CENTER_ADMIN_LOGIN`,
`CENTER_ADMIN_PASSWORD`); без пароля закрытый API недоступен никому. Экран `/network` — за входом.

## 3. Четыре канала

| Канал | Что | Как доезжает | Где и сколько хранится |
|---|---|---|---|
| Метрики | блок `sys` в heartbeat | heartbeat раз в 10 с (core NATS); центр пишет пачкой раз в 5 с | `branch_metrics` в БД центра, 48 ч |
| Важные логи | WARN, ERROR, жизненный цикл | файл → Vector → `BRANCH_LOG` (отделение) ⇒ `CENTER_LOG` (центр) → Loki | Loki, 7 дней |
| Полные логи | все уровни за интервал | по запросу: RPC `diag.logs` → `CENTER_LOG` → Loki | Loki с меткой выгрузки, 7 дней |
| Снимок | потоки JVM, БД, пул, outbox, NATS, конфигурация, диск, жизненный цикл | по запросу: RPC `diag.snapshot` | `branch_diagnostics`, 30 дней |

Heartbeat — core NATS: во время обрыва метрик нет (на графике пробел, в обзоре «нет связи»). Логи за время обрыва не
теряются.

## 4. Логи

**Файл на отделении.** Нода всегда пишет логи в файл в формате ECS (JSON-строка на событие): ротация по 20 МБ, 7 дней,
не больше 500 МБ, без сжатия — сборщик и выгрузка читают старые файлы как есть.

**События жизненного цикла** — строки с `event.kind=lifecycle`, уходят в центр независимо от уровня: `app.started`,
`app.stopping`, `config.applied`, `leaf.linked` / `leaf.unlinked`, смена состояния связи с брокером,
`db.stuck` / `db.answering` (раздел 8), `error.unhandled` (упавшая задача по расписанию). Внезапная смерть видна по
`app.started` без `app.stopping` перед ним.

**Vector на отделении** (свой образ, конфиг запечён, лимит памяти 64 МБ) читает файл, оставляет WARN, ERROR и
жизненный цикл, глушит повторы (не больше 30 строк в минуту на логгер и уровень — лишнее остаётся в файле) и кладёт
строки в стрим `BRANCH_LOG` локального NATS. Позиция в файле сдвигается только после подтверждения JetStream, повторы
отсекаются по хешу строки (`Nats-Msg-Id`).

**До центра** строки везёт сам NATS — тем же механизмом, что события: `BRANCH_LOG` (7 дней, 256 МБ) подключён
источником к `CENTER_LOG` (7 дней, 2 ГБ). В центре `LogShipper` забирает пачки до 500 строк и пишет в Loki,
подтверждая сообщения только после ответа Loki 2xx; Loki недоступен — пачка ждёт в `CENTER_LOG`, повтор с паузой
1–2–5–15–30 с. Метки Loki: отделение, уровень, источник (`stream` / `pull`), у выгрузки — свой `pull`.

**Полные логи по запросу.** `POST /api/v1/branches/{b}/diagnostics/logs` (`minutes` или `from`/`to`, уровень, подстрока,
до 100 000 строк, интервал до 7 дней). Нода читает свои файлы страницами по 5000 строк / 512 КБ, центр кладёт их в
`CENTER_LOG` → Loki, в ответе — число строк и ссылка на них в Grafana Explore. Пока не запросили, полные логи не
покидают отделение.

## 5. Метрики

**Блок `sys` в heartbeat** (≈ 600 байт): CPU процесса и системы, load average, heap, паузы GC, пул соединений БД
(занято / ждут / максимум), размер БД, свободный диск, число запросов, rps, p95 и доля 5xx своего API (только `/api/`,
без потоков SSE и файлов экранов), клиенты SSE, связь с центром и её RTT, переподключения к брокеру, ERROR и WARN в
логе за интервал, время работы и версия, время по системным часам (расхождение с центром).

**В центре** последний heartbeat каждого отделения ждёт в памяти и раз в 5 с одной транзакцией пишется пачкой:
обновляется реестр (`branches`, его читает обзор сети) и добавляется строка истории `branch_metrics` (разрешение 10 с,
хранение 48 ч). История — `GET /api/v1/branches/{b}/metrics?from&to`. Под рой (`ESUO-scale.md`, разделы 2–3) история —
числовые колонки в часовых партициях, у отделений за региональным хабом шаг 60 с, «на связи» — в узкой таблице
`branch_seen`.

**Grafana** (профиль `monitoring`): дашборды «ЕСУО · Отделение» (CPU, память, база, API, связь с центром, логи) и
«ЕСУО · Сеть» (сводка по всем). Grafana читает БД центра отдельной ролью `grafana_ro` — только `SELECT` на
`branches`, `branch_metrics`, `branch_alerts`; роль создаётся центром при старте, если задан `GRAFANA_DB_PASSWORD`.

## 6. Правила

`infrastructure/config/monitoring-rules.yml` — меняются без пересборки. Центр проверяет историю раз в 15 с; сработавшее
правило — аномалия `sys.*` в обзоре сети с готовым текстом.

| Правило | Условие | Важность | Текст в обзоре сети |
|---|---|---|---|
| `sys.cpu` | CPU > 90 % дольше 5 мин | предупреждение | ПК отделения не справляется: CPU N% уже M мин |
| `sys.slow_api` | p95 > 1500 мс дольше 3 мин | предупреждение | API отделения отвечает медленно: p95 N мс |
| `sys.db_pool` | запросы ждут соединения дольше 2 мин | предупреждение | Узкое место в базе: запросы ждут соединения |
| `sys.disk` | свободно < 10 % | критично | На диске отделения осталось N% |
| `sys.link` | > 5 переподключений за час | предупреждение | Нестабильная связь с центром: N переподключений за час |
| `sys.clock` | расхождение с центром > 60 с дольше 2 мин | предупреждение | Часы отделения расходятся с центром на N с |
| `sys.restart` | время работы уменьшилось (окно 30 мин) | информация | Приложение отделения перезапускалось в ЧЧ:ММ |

Все правила — один SQL-запрос в Postgres, история в память центра не грузится (`ESUO-scale.md`, раздел 2). Результат
проверки — таблица `branch_alerts` под advisory lock: при нескольких репликах центра считает одна, обзор читает
готовое. Продолжающееся срабатывание сохраняет момент начала. При `DEMO_MODE=true` длительности сокращаются в
10 раз (5 мин → 30 с), чтобы правило сработало на показе.

## 7. Снимок диагностики

`POST /api/v1/branches/{b}/diagnostics/snapshots` — снять, сохранить, вернуть; список — `GET …/diagnostics/snapshots`
(без содержимого), целиком — `GET /api/v1/diagnostics/snapshots/{id}`. Хранение 30 дней, «кто снял» — из токена.

Девять разделов: `app`, `jvm` (потоки по состояниям, заблокированные со стеком, deadlock'и, heap), `db_pool`, `db`
(активные запросы, кто кого блокирует, крупные таблицы, размер), `outbox`, `nats`, `config`, `disk`, `lifecycle`
(последние 20 событий жизненного цикла).

Снимок нужен ровно тогда, когда что-то сломалось, поэтому:

- каждый раздел — отдельно, общий дедлайн 8 с: упавший или зависший раздел приходит с ошибкой, остальные — как есть;
- `db_pool` читается без запроса к БД — при зависшей базе видно, сколько потоков ждут соединения;
- `db` ходит в базу **своим соединением мимо пула** (подключение 2 с, чтение 8 с, запрос 2 с) — показывает блокировку
  даже когда её жертвы заняли весь пул; каждый запрос раздела падает отдельно (размеры таблиц ждут ту же блокировку);
- раздел, зависший с прошлого снимка, не запускается повторно — повторные нажатия не выбирают пул;
- текст запросов обрезан до 200 символов, значений параметров в нём нет;
- ответ ≤ 512 КБ: при превышении сначала убираются стеки, потом самые большие разделы.

Замеры: обычный снимок — 0,1 с, 6 КБ; база заморожена (`docker pause`) — 8 с, разделы базы «timed out», пул, потоки,
NATS и жизненный цикл на месте; блокировка таблицы с занятым пулом — 10 заблокированных запросов и 17 ждущих
соединения видны в снимке.

## 8. Зависшая база ≠ нет связи

Найдено хаос-сценарием: блокировка таблицы заняла весь пул и все потоки общего планировщика, heartbeat перестал уходить,
и центр показал отделение как «нет связи» — хотя связь была.

Теперь heartbeat работает на своём потоке, а его часть из базы (очередь, окна, версии) ждёт не больше 3 с. Не успела —
heartbeat всё равно уходит: последние известные цифры очереди, свежий блок `sys` и `db_ok=false`. В обзоре сети
отделение на связи, аномалия «данные очереди не обновляются N с — база отделения не отвечает или ПК перегружен»,
срабатывает `sys.db_pool`. «Или ПК» — честно: при урезанном CPU чтение очереди тоже не укладывается в 3 с. Размер БД
в `sys` читается в фоне и тоже не держит heartbeat.

версия; кнопки «Подробные логи (30 мин)» (появляется ссылка на них в Grafana) и «Снять диагностику» (снимок

Аномалии `sys.*` в общем списке — текстом правила, а не кодом.

## 10. Развёртывание

Профиль compose `monitoring`: Loki и Grafana у центра, Vector — отдельный контейнер рядом с каждой нодой. Без профиля
состав контейнеров прежний: метрики, правила, снимки и выгрузка логов — часть центра и ноды, важные логи копятся в
стримах. Раздельный деплой — `deploy/center` (с мониторингом центра), `deploy/branch` (Vector в compose отделения) и
`deploy/swarm`; корневой compose собирается из них (`ESUO-scale.md`, раздел 8).

| Переменная | Где | Зачем |
|---|---|---|
| `CENTER_ADMIN_LOGIN`, `CENTER_ADMIN_PASSWORD` | центр | вход оператора сети; без пароля закрытый API недоступен |
| `LOKI_URL` | центр | куда отправлять логи; пусто — ждут в `CENTER_LOG` |
| `GRAFANA_PUBLIC_URL` | центр, Grafana | ссылки на логи и дашборд; пусто — без ссылок |
| `GRAFANA_DB_PASSWORD` | центр, Grafana | роль `grafana_ro`; пусто — без панелей из БД центра |
| `GRAFANA_ADMIN_PASSWORD`, `GRAFANA_ANONYMOUS` | Grafana | на публичном сервере анонимный просмотр выключен |
| `LOG_FILE` | нода | файл логов; пусто — только консоль, выгрузка и раздел `lifecycle` недоступны |
| `METRICS_RESOLUTION`, `METRICS_RESOLUTION_REGIONAL` | центр | шаг истории метрик: 10 с; у отделений за региональным хабом — 60 с |
| `METRICS_RETENTION`, `METRICS_MAX_SIZE` | центр | хранение истории 48 ч и страховка диска 100 ГБ |
| `CENTER_HEAP`, `CENTER_DB_SHARED_BUFFERS` | центр | куча центра и память его Postgres; на сервере с роем — 4g и четверть ОЗУ |
| `DEMO_MODE` | центр | длительности правил ×0,1 |

Попутно: прокси связи отделений на стенде поднимаются после перезапуска Docker (`restart: unless-stopped`); связь,
разорванная хаос-скриптом, остаётся разорванной.

## 11. Хаос-сценарий и стресс-скрипты

`./scripts/demo/run.sh health` — 18 проверок, ход событий повторяется (одинаковая подпись в повторных прогонах):

1. узлу оставлена 0,1 CPU под нагрузкой → «ПК отделения не справляется: CPU 97% уже 1 мин»;
2. зависшая блокировка таблицы под нагрузкой → отделение на связи, «данные очереди не обновляются», «запросы ждут
   соединения», снимок показывает 10 заблокированных запросов; после снятия — данные снова свежие;
3. обрыв связи и `kill -9` приложения → после восстановления «перезапускалось в …», ошибки до и после падения доехали
   в Loki со своим временем;
4. всё возвращено — процессор, база, связь (и при Ctrl+C).

Каждую поломку можно устроить отдельно — скрипт раз в 10 с печатает, что видит центр, и сам возвращает всё назад;
режимы `start` / `stop` — для своих сценариев:

| Скрипт | Поломка |
|---|---|
| `scripts/chaos/cpu-starve.sh b01 [сек] [доля CPU]` | урезанный CPU + нагрузка на API |
| `scripts/chaos/db-lock.sh b01 [сек] [таблица]` | блокировка таблицы + 25 клиентов, пул занят целиком |
| `scripts/chaos/db-freeze.sh b01 [сек]` | база не отвечает вообще (`docker pause`) |
| `scripts/chaos/node-kill.sh b01` | `kill -9` приложения и подъём |
| `scripts/chaos/cut-branch-link.sh b01 [restore\|status]` | обрыв связи с центром |

## 13. Масштаб: 40 000 отделений [Расчёт]

> Сделано и проверено на 250 000 отделений — `ESUO-scale.md`. Ниже — исходная оценка.

- Важные логи: ~50 строк WARN+ в день на отделение → ≈ 2 млн в сутки, ≈ 23 строки/с на сеть — для Loki немного.
- 40 000 источников у `CENTER_LOG` — та же задача, что у `CENTER_EVT`; решается региональным уровнем NATS.
- `branch_metrics` при шаге 10 с — 4 000 строк/с, ≈ 690 млн за 48 ч: для одной PostgreSQL много. Для большой сети —
  шаг 60 с (≈ 115 млн, `METRICS_RESOLUTION=60s`), разбиение по дням или колоночное хранилище.
- Правила сейчас раз в 15 с перечитывают час истории (из-за окна `sys.link`); для большой сети — прирост по двум точкам.

## 14. Решения и компромиссы

| Решение | Почему | Цена / путь развития |
|---|---|---|
| Важные логи — push через NATS, полные — pull по запросу | канал отделения не забивается; полные логи нужны редко | — |
| В центре свой `LogShipper`, а не Vector | NATS-источник Vector подтверждает сообщение при чтении — потеря при сбое | — |
| Метрики в PostgreSQL центра, а не в Prometheus | нет нового компонента; обзор, правила и Grafana читают одну таблицу | TimescaleDB или Prometheus remote write для большой сети |
| Правила по истории под advisory lock, результат в таблице | heartbeat при нескольких репликах центра идёт через queue group — память одной реплики неполна | инкрементальный расчёт |
| p95 своим фильтром: только `/api/`, без SSE | SSE живут минутами, файлы экранов быстрые — оба искажают перцентиль | — |
| Снимок: разделы порознь, `db` — своё соединение | снимок снимают, когда всё плохо; один зависший запрос не должен съесть ответ | — |
| Heartbeat на своём потоке, часть из БД — с таймаутом | признак жизни не должен ждать задач, застрявших на базе | — |
| Один Loki | достаточно для стенда | Loki в режиме simple scalable, S3-совместимое хранилище |
| Нода пишет файл логов всегда, Vector — только в профиле | выгрузка работает и без мониторинга; базовый стенд не тяжелеет | — |
| Метки Loki: отделение, уровень, источник (+ `pull`) | малая кардинальность; повторная выгрузка старого интервала иначе отвергается Loki как out-of-order | — |

## 15. Стек и лицензии

| Компонент | Лицензия | Где |
|---|---|---|
| Vector 0.58 | MPL-2.0 | сбор логов на отделении |
| Grafana Loki 3.7 | AGPLv3 | хранение логов у центра, профиль `monitoring` |
| Grafana 13 | AGPLv3 | дашборды и просмотр логов, профиль `monitoring` |

Loki и Grafana ставятся без изменений отдельными сервисами и в продукт не встраиваются; обязательства AGPL возникают
при изменении их кода и предоставлении изменённой версии — у нас этого нет. Оценка команды, не юридическое заключение.

## 16. Ограничения

- ~~Правила перечитывают час истории каждые 15 с~~ — сделано одним SQL (`ESUO-scale.md`, раздел 2).
- Выгрузка логов: если файл ротируется между страницами, хвост старого файла может не попасть; если выгрузка упала на
  середине, первые страницы уже в Loki; две одинаковые строки в одну миллисекунду склеиваются.
- При урезанном CPU «данные очереди не обновляются» может появляться и без проблем с базой — текст это говорит.
- Раздельный деплой (центр и отделения на разных ПК) с мониторингом в этой работе не поднимался — только стенд «всё в
  одном».
- Ограничения частоты попыток входа в центр нет — как и на ноде.
