## 1. Коротко

Рой из 250 000 виртуальных отделений (4 региона по 62 500, heartbeat раз в 10 с — 25 000 в секунду, до 2 800
событий в секунду) роняли центр по памяти, по базе и по брокеру. Теперь на том же ноутбуке:

| Что | Было | Стало |
|---|---|---|
| Правила мониторинга | грузили час истории в память: OOM на 125 000 | один SQL в Postgres: 0,3 с на 40 000, 1,7 с на 125 000, 5 с на 250 000 |
| «На связи» | скакало 57–250 тыс. — запись не успевала | 250 002 во всех замерах за 8 мин |
| События | — | 1 448 278 подтверждено роем = 1 448 278 в базе центра |
| Брокер (хаб NATS) | 8,2 ГБ прочитанных событий; после сбоя — 5,7 ГБ памяти и падения по кругу | в потоке ~200 непрочитанных событий, хаб 268 МБ |
| Вкладка `/network` | «Конфигурация» не открывалась (ответ 51 МБ за 27 с раз в 15 с) | 4–5,5 МБ памяти страницы на любой странице |
| Публичный список отделений | один анонимный запрос — OOM центра | 25 КБ за 21 мс; 100 запросов по 10 параллельно — все за ≤ 0,06 с |
| Центр завис | жил «зомби» без работы | выход при OOM, Docker поднимает заново, дамп кучи |
| Видно ли, что с самим центром | нет | Prometheus, дашборд «ЕСУО · Центр», строка «Центр» в `/network`, снимок центра |

## 2. Правила мониторинга — в Postgres

Раньше центр раз в 15 с читал в память час истории всех отделений и считал правила в Java: на 125 000 отделений —
3,5 млн строк и OOM. Теперь все правила — **один SQL-запрос**, собранный при старте из
`infrastructure/config/monitoring-rules.yml` (`RuleQuery`); в Java приходят только сработавшие.

- **Порог** (`cpu > 90% 5 мин`): сначала дешёвый отбор без сортировки (последнее значение, держится ли оно, есть ли
  плохие точки), потом точная проверка непрерывности — только для кандидатов.
- **Доля, прирост, перезапуск**: прирост — по первой и последней точке окна через индекс; перезапуск процесса
  определяется по времени старта по часам самого узла (±5 с), а не по задержке доставки — нагруженный центр, прочитавший
  heartbeat поздно, не выдумывает перезапусков.
- **Свежесть**: отделение, замолчавшее дольше `max(2 мин, 3 × шаг метрик)`, порог не держит.
- Продолжающееся срабатывание сохраняет момент начала; запись в `branch_alerts` — массивами, переписываются только
  изменившиеся строки (на 70 000 срабатываний нет предела в 65 535 параметров JDBC).

**История метрик** `branch_metrics`: числовые колонки вместо JSON (≈ 250 байт строка вместе с индексами — в ~5 раз
меньше), **часовые партиции** с партицией по умолчанию (вставка никогда не падает из-за отсутствующей партиции),
удаление старых часов целиком (`DROP`, а не `DELETE` миллионов строк), страховка диска `METRICS_MAX_SIZE` (100 ГБ).
Шаг: 10 с у настоящих отделений, 60 с у отделений за региональным хабом (`METRICS_RESOLUTION_REGIONAL`): у роя — минута,
у демо-отделений графики остаются подробными. 40 000 отделений на 60 с — ≈ 14 ГБ за 48 ч **[Расчёт]**.

## 3. Запись heartbeat: «на связи» отдельно от содержимого

25 000 heartbeat в секунду центр копит в памяти и раз в 5 с пишет пачками. Что пришлось сделать на 250 000:

1. **Память пути** (`7debbee`): сброс пачками по 5 000 в транзакции с освобождением записанного, тело heartbeat в UTF-8
   байтах, строка метрик — массив, реестр отделений известен со старта (иначе после перезапуска — волна регистрации).
2. **Содержимое роя — раз в минуту**: JSON heartbeat (~1,8 КБ) у отделений за региональным хабом пишется с шагом их
   метрик, своя фаза у каждого отделения — не все в одном сбросе.
3. **«Видели» — в узкой таблице `branch_seen`** (id, время). JSON меньше порога TOAST (2 КБ) и лежит прямо в строке
   `branches`: обновление одного времени копировало всю строку. 250 000 обновлений: 7,2–7,7 с в `branches` против
   0,6–0,8 с в `branch_seen` **[Проверено на стенде, копия таблицы]**. «Последний раз слышали» =
   `GREATEST(branches.last_heartbeat_at, branch_seen.seen_at)` — так читают обзор, сводка, страницы, конфигурация и
   счётчик на дашборде.
4. **«Видели» — первым проходом**: сброс сначала отмечает всю пачку (~1 с на 250 000), потом пишет содержимое и метрики.
   «На связи» не ждёт тяжёлой записи и не падает вместе с ней.
5. **Postgres центра под сеть**: `shared_buffers` 1 ГБ (`CENTER_DB_SHARED_BUFFERS`), WAL 4 ГБ, контрольная точка
   15 мин, `wal_compression`, автоочистка без тормоза.

Итог на 250 000: сброс 5 с в среднем; к концу часа растёт до 15–18 с (индекс часовой партиции метрик перестаёт влезать
в память), но на «на связи» это больше не влияет.

## 4. Поток событий центра — буфер доставки, а не архив

`CENTER_EVT` хранил **прочитанные** события 30 дней с окном дедупликации 1 ч, хотя хранилище событий сети — таблица
`events`. За день прогонов роя — 8,2 ГБ; после нештатной остановки хаб при восстановлении вырастал до 5,7 ГБ памяти,
и ядро виртуалки Docker (8 ГБ) убивало его по кругу — вместе с ним упал центр. Теперь:

- событие лежит в `CENTER_EVT`, **пока его не подтвердят все читатели центра** — запись в базу, уведомления,
  применение конфигурации, callback МП, — и уходит из брокера; пока центр недоступен, поток копит всё непрочитанное;
- 30 дней — предел только для того, что больше никто не читает (брошенный читатель);
- окно дедупликации — 2 мин: дубли отсекает база (`ON CONFLICT (event_id)`);
- читатель `analytics-ingest` создаётся вместе с потоком, до подключения источников: событие, пришедшее раньше первого
  читателя, NATS при таком хранении выбросил бы;
- поток старого центра переводится при подключении; поток, созданный заново (потерян том хаба), получает источники
  снова — раньше флаг `source_attached` в базе их не возвращал, и события отделений навсегда оставались в их буферах.

Буферы отделений и регионов (`BRANCH_EVT`, `REGION_EVT`) — по времени, как были: «до подтверждения» там удаляло бы
событие в момент отправки в хаб, обрыв посреди передачи терял бы его.

## 5. Центр не «зомби»

- `CENTER_HEAP` (2g; на сервере с роем — 4g), выход при `OutOfMemoryError` и перезапуск Docker'ом; первый дамп кучи
  остаётся в томе `center-dumps` для разбора.
- Проверка здоровья центра — на отдельном порту управления 9081 (только localhost); `/readyz` и `/livez` — на основном.
- Лимиты памяти в compose: хаб NATS 2 ГБ с `GOMEMLIMIT`, регионы 1 ГБ, Loki и Grafana 512 МБ, Prometheus 1 ГБ:
  сервис, вышедший за свою память, перезапускается один и не забирает память у центра.

## 6. Мониторинг самого центра

- **Prometheus** (профиль `monitoring`): метрики центра (`/actuator/prometheus` на 9081), хаба NATS (экспортёр, включая
  соединения регионов и отделений) и Postgres центра (экспортёр).
- **Метрики центра**: сброс heartbeat (время, отделений за сброс, буфер), строки истории и потерянные, проход правил и
  сбои, срабатывания, приём и ошибки событий, отставание записи событий, регистрация отделений, отправка логов в Loki,
  снимок сети, отделения на связи и без связи, размер истории метрик.
- **Дашборд «ЕСУО · Центр»** (33 панели): CPU, куча, GC, потоки, задачи центра, сброс, правила, события, хаб, база,
  логи центра. «Сеть» и «Отделение» переделаны под рой (топ-10, таблицы ограничены).
- **Снимок центра** `POST /api/v1/center/diagnostics[?heap=true]` (оператор сети): какие потоки едят CPU за секунду —
  Java-потоки со стеками и потоки самой JVM (GC, JIT) из `/proc`; куча, GC, очереди, пул БД, NATS, задачи; по
  `heap=true` — что лежит в куче (гистограмма классов после полной сборки). Отвечает на вопрос «это GC или код».
- **Логи центра** — файл ECS JSON с ротацией, `vector-center` везёт его в Loki (`service=center`).

## 7. Экран `/network` для сотен тысяч отделений

Ничего на экране не растёт с сетью: главная — только агрегаты, списки — страницами по 24.

- **Сервер**: общий **снимок сети** (`NetworkSnapshot`) — кто на связи, аномалии и тяжесть каждого отделения, суммы по
  сети и по регионам. Строится по запросу курсором (сеть не попадает в память одним списком), не чаще чем раз в
  `clamp(3 × время сборки, 1 с, 5 с)`, одним потоком на всех; никто не смотрит — нагрузки нет. Карточки — только для
  показанных отделений и свежие из базы: скрипты демо и хаоса видят обрыв связи без задержки кэша.
- **API**: `/network/summary` (плитки регионов с очередью отделений на связи и худшим), `/network/regions/{r}`,
  `/network/branches?q&status&region&anomaly`, `/network/branches/{id}`, `/network/center` (строка «Центр»);
  публичный `/api/v1/branches?q&offset&limit` → `{total, offset, limit, items}`; `/api/v1/config` — страница отделений
  с поиском и регионом; `/network/overview` (все карточки) — до 1000 отделений, дальше `422 NETWORK_TOO_LARGE`.
- **Экран**: главная — счётчики, строка «Центр» (CPU, GC, куча, heartbeat/с, события/с, сброс, правила; ссылка на
  Grafana), аномалии по типам (клик — список с фильтром), плитки регионов, худшие 10, свои отделения полными карточками;
  страница региона — сводка, худшие, поиск, фильтр, страницы; панель отделения `/network/b/:id` (у роя — только
  «Графики»: узла, который ответил бы на логи и снимок, нет); «Конфигурация» — страницы, поиск, отделение выбирается из
  строки; у клиента — поиск отделения.

## 8. Compose: центр, отделение и рой — отдельно

| Файл | Что внутри |
|---|---|
| `deploy/center/docker-compose.yml` | центр: база, хаб, центр, симуляторы МП и уведомлений; профиль `monitoring` — Loki, Grafana, Prometheus, экспортёры, сборщик логов центра |
| `deploy/branch/services.yml` | шаблоны отделения: база, leaf, нода, сборщик логов (профиль `monitoring`) |
| `deploy/branch/docker-compose.yml` | одно отделение где угодно (`BRANCH_ID`, `CENTER_HOST`); несколько на машине — разные env-файлы |
| `deploy/swarm/docker-compose.yml` | экземпляр роя: четыре региональных leaf и `swarm-sim` (профиль `run`) |
| `docker-compose.yml` | «всё в одном» для жюри: всё берёт из `deploy/` через `extends`, добавляет сети, имена контейнеров, порты на localhost, прокси связи для хаоса, пульт демо |

Команда жюри прежняя (`docker compose up -d --build`); развёрнутая конфигурация корня совпала с прежней везде, кроме
задуманного (лимиты памяти, единые имена переменных, исправленные мелочи). Мониторинг лежит с тем, к чему относится:
мониторинг центра — в `deploy/center`, сборщик логов отделения — в `deploy/branch`. Имена переменных одинаковы во всех
файлах (`DB_PASSWORD`, `JWT_SECRET`, `LEAF_PASSWORD`…); в `deploy/center/.env` прежние `CENTER_DB_PASSWORD`,
`CENTER_JWT_SECRET`, `LEAF_SHARED_PASSWORD` заменены на общие. В шаблонах отделения нет `depends_on` и обязательных
переменных: при `extends` они переходят к наследнику, а у b01 и b02 свои имена сервисов.

## 9. Рой

- `--date ГГГГ-ММ-ДД` — дата виртуального дня: в модели потока воскресенье закрыто, прогон в воскресенье без даты
  шлёт только heartbeat.
- Контейнером: `docker compose --profile swarm-run run --rm swarm-sim --branches N` — регионы и папка отчёта зашиты в
  entrypoint, аргументы добавляются к ним.
- Перед замером: обнулить регионы (`docker compose --profile swarm up -d --force-recreate nats-region-1 … nats-region-4`)
  — их потоки живут в слое контейнера; иначе дни прогонов копятся. См. раздел 12 про NATS.

## 10. Решения и компромиссы

| Решение | Почему | Цена |
|---|---|---|
| Правила одним SQL | история не грузится в JVM; Postgres делает это быстрее и без памяти центра | правила — только из поддерживаемых видов (порог, доля, прирост, перезапуск) |
| Числовые колонки истории вместо JSON | в ~5 раз меньше строк на диске | новая метрика — новая колонка (`MetricColumns`) |
| Часовые партиции, `DROP` старых | удаление — мгновенно; вставка не падает | к концу часа индекс горячей партиции растёт (раздел 3) |
| Шаг 60 с у роя, 10 с у своих | у роя на порядок меньше записи, демо-графики подробные | цифры очереди у отделений роя в обзоре — до минуты давности |
| «Видели» в отдельной таблице | обновление ~50 байт вместо копии строки ~1,8 КБ | ещё один `JOIN` у читателей «на связи» |
| `CENTER_EVT` до подтверждения | брокер — буфер, база — хранилище; поток почти пуст | событие, которое никто не читает 30 дней, удаляется |
| Снимок сети раз в 1–5 с | сотни тысяч отделений судятся раз, а не на каждый опрос каждой вкладки | счётчики и фильтры — до 5 с давности (карточки свежие) |
| `/network/overview` до 1000 | все карточки сразу роняли центр | скрипты большой сети — через summary и страницы |
| Корень через `extends`, без скрипта | один источник описаний, команда жюри прежняя, гибкость compose | шаблоны отделения — отдельный файл |
| Без лимита памяти у центра | куча ограничена `-Xmx`; несогласованный лимит убивал бы контейнер | нативная память центра не ограничена |

## 11. Как проверить

```bash
docker compose --profile swarm up -d --force-recreate nats-region-1 nats-region-2 nats-region-3 nats-region-4
java -Xmx4g -jar java-backend/swarm-sim/target/swarm-sim-0.0.1-SNAPSHOT.jar --branches 250000 --duration 8m \
     --date 2026-10-05 --start 12:00
node frontend/e2e/measure-network.mjs          # память вкладки и цена API по всем страницам /network
```

Потери: `events_acked_total` из отчёта роя = `SELECT count(*) FROM events WHERE branch_id LIKE 's%'`. Состояние центра —
дашборд «ЕСУО · Центр» и строка «Центр» на `/network`. Тесты центра — 218 (`./mvnw -pl center-app -am test`), e2e — 16 тестов
на двух размерах экрана.

## 12. Ограничения и что дальше

- **NATS 2.10.26 → 2.15.0** (решено, делается следующим): в 2.10 поток-источник, созданный заново (переустановили ПК
  отделения, стёрли хранилище регионального leaf), хаб продолжает читать со старого номера сообщения — события до этого
  номера центр пропускает ([nats-server#6206](https://github.com/nats-io/nats-server/issues/6206), исправлено в 2.15.0).
  Пока это ограничение: после такого случая — перезапуск хаба. На стенде однажды не дошло самое первое событие нового
  региона (1 из 365, в первые миллисекунды жизни его потока); отдельно на 2.10.26 и 2.15.0 не воспроизвелось —
  проверить после обновления.
- Сброс heartbeat к концу часа — 15–18 с на 250 000 на ноутбуке; путь, если понадобится: партиции метрик по 15 минут.
- Раздельный запуск `deploy/center`, `deploy/branch`, `deploy/swarm` проверен через `docker compose config`; живой
  запуск трёх проектов на разных машинах — после обновления NATS.
- Проход правил на 250 000 — ~5 с при периоде 15 с: запас есть, но не бесконечный.
