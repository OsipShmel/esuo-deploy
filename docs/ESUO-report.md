# ЕСУО: отчёт о проделанной работе

Электронная система управления очередью для сети почтовых отделений. Команда «Long Honey Road».

Состояние: ветка `wip/scale-monitoring`, 2026-10-04. Как устроено внутри — в техническом
[дизайн-документе](ESUO-design-doc.md); ссылки вида «ДД §6» ведут в него. Как запустить и проверить самому —
[`demo/run-guide.md`](demo/run-guide.md).

---

## 1. Коротко

**Проблема.** Очередь в отделении — это часы, которые теряют клиенты, и смены, которые руководитель планирует на
глаз. Типичная электронная очередь при этом зависит от центрального сервера: пропала связь с головным офисом —
встал зал.

**Что мы сделали.** Сеть отделений, где каждое отделение — самостоятельная ячейка очереди, а центр связывает их
в сеть, но не держит на себе обслуживание.

Пять вещей, которые отличают решение:

1. **Отделение работает без центра полностью, а не «в аварийном режиме».** Обрыв связи посреди дня: зал продолжает
   выдавать талоны и вызывать клиентов, после восстановления всё накопленное доезжает в центр само. Отделение может
   быть отрезано неделю — ни одно событие не потеряется. Демо-сценарий `link-cut`: 10 проверок из 10.
2. **Подключить новое отделение = запустить три контейнера и указать адрес центра.** В центре не настраивается
   ничего: отделение само появляется в сети, получает правила и начинает отдавать события. Работает одинаково в
   локальной сети и через интернет, за NAT и без белого IP.
3. **Честная очередь с гарантией.** У каждого клиента есть срок, к которому его обещано вызвать; просроченные идут
   первыми, никто не ждёт бесконечно. Два окна никогда не вызовут одного человека — это проверено тестом с
   одновременными вызовами. Клиент видит не «ожидайте», а интервал «вызов около 10:42 (10:38–10:50)», и если
   оценки нет — система говорит честно, а не выдумывает.
4. **Система заранее знает, сколько окон нужно, и сама не пускает перегрузку.** Прогноз длительности (ML-модель
   + статистика) считает нагрузку по часам. В пенсионный день с прогнозом среднее ожидание **3,9 минуты вместо
   94**, просроченных талонов **0 вместо 142**; на живом стенде в день «хуже плана» очередь к полудню **16 человек
   вместо 72**. При угрозе перегрузки система сама закрывает часть онлайн-записи на пиковые часы — уже записанных
   не трогает.
5. **Центр видит всю сеть — и очереди, и здоровье ПК отделений — и выдерживает 250 000 отделений.** Завис ПК или
   база отделения — центр показывает, что именно сломалось, раньше, чем позвонят из отделения; логи и снимок
   диагностики — по кнопке, без выезда и удалённого доступа. На ноутбуке центр принял 250 000 виртуальных отделений:
   1 448 278 событий отправлено — 1 448 278 записано, ни одного потерянного.

```
                    ┌──────────────── ЦЕНТР ────────────────┐
   клиент из  ───▶  │  шлюз · реестр сети · правила         │
   интернета        │  уведомления · мобильное приложение   │
                    │  обзор сети · мониторинг · Grafana    │
                    └───────▲───────────────▲────────▲──────┘
                            │ NATS leaf     │        │ региональный NATS
                  исходящее соединение, инициирует отделение / регион
                            │               │        │
               ┌────────────┴───┐   ┌───────┴──────┐ ┌┴──────────────┐
               │ ОТДЕЛЕНИЕ b01  │   │ ОТДЕЛЕНИЕ b02│ │ РЕГИОН        │
               │ очередь · БД   │   │ очередь · БД │ │ тысячи        │
               │ табло · окна   │   │ табло · окна │ │ отделений     │
               └────────────────┘   └──────────────┘ └───────────────┘
```

## 2. Архитектура: почему это просто масштабируется

### Отделение — как касса, которая не встаёт без интернета

Всё, что нужно залу, живёт в отделении: база, логика очереди, экраны. Центр нужен для того, что по смыслу сетевое:
запись из интернета, правила для всех отделений, обзор и мониторинг сети, уведомления. Если центр недоступен,
отделение этого почти не замечает: клиент из интернета получает понятный ответ «отделение временно недоступно», а
зал работает как обычно.

### Связь через NATS — один лёгкий брокер вместо зоопарка

Отделения и центр общаются через NATS — компактный брокер сообщений одним бинарником. В каждом отделении стоит свой
локальный NATS (leaf), который сам дозванивается до центра. Это даёт сразу всё, что обычно собирают из нескольких
систем:

| Что нужно | Как обычно | Как у нас |
|---|---|---|
| Отделение за NAT, без белого IP | VPN, проброс портов | отделение само открывает исходящее соединение |
| Не терять события и логи при обрыве | свой буфер, ретраи, дедупликация | события и важные логи лежат на диске отделения и докачиваются брокером сами (буфер 7 дней) |
| Правила и записи для офлайн-отделения | повторная отправка вручную | ждут в центре и приходят сами после восстановления |
| Центр спрашивает отделение (свободные слоты, логи, диагностика) | HTTP с входящим доступом | запрос-ответ через тот же канал; офлайн-отделение распознаётся мгновенно, без ожидания таймаута |
| Регистрация нового отделения | ручная настройка центра | первое сообщение «я жив» регистрирует отделение автоматически |

**Что это значит на практике:**

- **Масштабирование.** Сто первое отделение подключается так же, как второе: те же три контейнера, три параметра
  (код отделения, адрес центра, пароль). Центр не участвует в обслуживании зала, поэтому скорость отделения не
  зависит от размера сети. Для сотен тысяч отделений между ними и центром стоят региональные NATS: центр подключает
  поток событий региона один раз, а не каждого отделения (ДД §3.8).
- **Проверено на 250 000 отделений.** Рой виртуальных отделений на том же ноутбуке: 25 000 сообщений «я жив» в
  секунду, до 2 800 событий в секунду. Все 250 000 «на связи» во всех замерах, события — без потерь, центр без
  перезапусков; 40 000 новых отделений регистрируются за минуту (ДД §12).
- **Переносимость.** Одна и та же сборка работает на одном ноутбуке (центр + два отделения одной командой), в
  локальной сети и с центром в облаке. Центр, отделение и рой описаны отдельно — каждый запускается на своей
  машине. Все образы — компактные alpine.
- **Лёгкость.** На ПК отделения — только база, брокер, одно приложение, в которое уже встроены все экраны, и
  сборщик логов. Ни отдельного веб-сервера, ни VPN, ни репликации базы.

Подробнее — ДД §2–3, §12, §16.

## 3. Алгоритм очереди

**Каждому — срок.** Когда клиент получает талон, система назначает ему срок вызова: по QR обычному клиенту —
20 минут, пенсионеру — 15, особой категории — 10; для записи срок привязан к слоту. Приоритет выражен сроком, а не
отдельной очередью: пенсионер не обгоняет всех навсегда, он получает более ранний срок.

**Как окно выбирает следующего.**

1. Если кто-то уже просрочен — вызывается самый давно просроченный. Нарушенное обещание не оптимизируют, его
   исправляют.
2. Если несколько клиентов подходят к сроку почти одновременно (в пределах 5 минут) — окно берёт того, чья услуга
   короче: так за то же время обслуживается больше людей, и ничей срок не нарушается. В подобранном примере
   «посылка на 10 минут и письмо на 1 минуту» среднее ожидание падает **с 300 до 30 секунд**.
3. Иначе — строго по сроку.

**Почему не «самые короткие вперёд» всегда.** Мы посчитали: такое правило снижает среднее ожидание на треть, но
клиенты с долгими услугами начинают ждать в полтора раза дольше. Для государственного сервиса гарантия «вас вызовут
в срок» важнее среднего, поэтому оптимизация разрешена только внутри 5-минутного окна. Это сознательный выбор.

**Двойного вызова не бывает.** Два окна нажимают «Следующий» в одну миллисекунду — каждое получает своего клиента.
Как в кинотеатре: место, которое уже держит один кассир, второй просто не видит и продаёт следующее. Защита
четырёхслойная, последний слой — ограничение в самой базе данных. Проверено тестом с одновременными вызовами из двух
окон на 40 талонах.

**Спорные ситуации разобраны:** клиент не подошёл (два повторных вызова, затем «не явился»), окно закрывается с
клиентом у стойки (клиента дообслуживают или возвращают в очередь без потери места), перенаправление в другое окно
или на другую услугу, возврат в очередь, перенос, опоздание на запись. Демо-сценарий `disputes`: 22 проверки из 22.

**Всё объяснимо.** Каждый вызов пишется в журнал со всеми кандидатами и причиной выбора. На вопрос «почему вызвали
не меня» есть ответ.

**Всё настраивается без переразвёртывания.** Сроки, окно терпимости, число повторных вызовов, политика опозданий и
ещё около 30 параметров меняются в центре и доезжают до отделений на лету, с версией.

Подробнее — ДД §5–6.

## 4. Прогноз и планирование нагрузки

### Прогноз длительности: ML-модель + статистика

Система оценивает, сколько займёт обслуживание конкретного клиента у конкретного сотрудника в конкретный час.
Работает в связке: обученная ML-модель и, как страховка, статистика по срезам (каскад). Модель обучается вне
отделения и приезжает к нему вместе с правилами, поэтому отделение не зависит от доступности ML вообще: нет модели —
работает статистика, нет статистики — разумное значение по умолчанию.

Эффект измерен сквозной симуляцией рабочего дня (синтетический мир с известными истинными параметрами,
воспроизводимо одной командой, `docs/demo/ml-report.md`). По прогнозу строится план окон на день, день проигрывается,
меряется фактическое ожидание:

| День | Ожидание без прогноза | Ожидание с ML + каскад | Просроченных талонов |
|---|---|---|---|
| Пенсионные выплаты | 94,4 мин | **3,9 мин** (в 24 раза меньше) | 142 → **0** |
| Обычный | 109,4 мин | **3,3 мин** (в 33 раза меньше) | 85 → **2** |
| Пенсионные, поток на 30 % выше плана | 75,3 мин | **15,3 мин** (в 5 раз меньше) | 139 → **65** |
| Выходной | 2,8 мин | **1,9 мин** | 0 → 0 |

Откуда эффект: без прогноза отделение считает «5 минут на любую услугу» и недооценивает нужное число окон на
21–45 %. С прогнозом ошибка плана — в пределах нескольких процентов. Плюс:

- обещание клиенту точнее в 6 раз: ошибка времени вызова **9 минут вместо 57** в пенсионный день;
- ошибка оценки длительности на **36 % ниже**, чем у константы, и совпадает с теоретическим пределом (112,6 с
  против 112,8 с у «оракула», который знает истинные параметры);
- интервал «10:38–10:50» честный: факт укладывается в него в **89 %** случаев;
- руководитель видит понятные фразы: «сотрудник обслуживает в 1,37 раза дольше среднего», «пенсионер на финансовых
  услугах — в 1,51 раза дольше».

### То же на живом стенде: два отделения, один день

`./scripts/demo/run.sh pension-ab` проигрывает одну и ту же трассу пенсионного дня (поток на 30 % выше плана) на двух
отделениях сразу. b01 работает без прогноза, b02 — с историей и моделью; руководитель каждого утром ставит смену по
прогнозу своего отделения:

| 08:50–12:30 | b01, без прогноза | b02, с прогнозом |
|---|---:|---:|
| Окно-часов в смене | 12 | 19 |
| Среднее ожидание | 31,6 мин | **14,7 мин** |
| Максимальное ожидание | 97,6 мин | **42,0 мин** |
| Очередь к 12:30 | 72 | **16** |
| Запись из мобильного приложения на 10:00 | принята в перегруженный час | **отклонена заранее** (`BOOKING_LIMITED`) |

Перегружены оба — пять окон физически не вытягивают такой поток. Разница в том, что b02 знало это утром: поставило в
смену всех и не приняло лишнюю запись. Полный отчёт прогона — `docs/demo/jury/ab-report.md`.

### Планирование нагрузки: система не ждёт, пока очередь вырастет

- **Профиль дня.** Обычный день, выходной, день пенсионных выплат (поток ×1,8, почти половина — пенсионеры). Даты
  выплат рассылает центр, руководитель может выбрать профиль вручную.
- **Прогноз по часам.** Сколько придёт людей, сколько это работы в минутах окна, сколько окон нужно.
- **Уровень нагрузки:** зелёный, жёлтый (очередь не разберётся за 15 минут), красный (за 30 минут или поток превышает
  мощность открытых окон). Уровень не мигает: чтобы подняться — 2 минуты устойчивого превышения, чтобы опуститься —
  10 минут заметно ниже порога.
- **Что система делает сама:** на жёлтом оставляет для новой записи только половину слотов этого часа, на
  красном закрывает запись на час полностью. Уже записанные клиенты сохраняют запись. Клиент видит закрытые часы
  заранее, а не получает отказ в последний момент.
- **Что решает человек:** открыть окно. Система рекомендует это **по прогнозу, до того как очередь вырастет**, с
  названием услуги и списком окон, которые могут её взять.
- **Журнал решений:** каждая смена уровня записана с цифрами и причиной («поток выше прогноза», «медленное
  обслуживание», «мало окон», «пик записи», «хвост просроченных»). Центр отмечает отделение, которое в красной
  зоне дольше 15 минут.

## 5. Устойчивость и мониторинг

| Что сломалось | Что происходит | Доказательство |
|---|---|---|
| Пропала связь с центром | зал работает полностью; клиент из интернета получает понятный отказ; QR на табло в режиме `auto` переключается на адрес отделения; после восстановления события и логи доезжают сами, со своим временем | демо `link-cut`: 10/10 — отделение «нет связи» в центре, табло работает, клиент, выданный во время обрыва, обслужен, накопленные события доехали |
| Перезапуск сервера отделения | очередь, вызванный клиент, занятое окно, неотправленные события — всё на месте; таймеры повторного вызова продолжаются с правильного момента | тест `RestartRecoveryIT` |
| Завис ПК, база или приложение отделения | центр показывает, что именно: «ПК не справляется: CPU 97 %», «данные очереди не обновляются — база не отвечает», «приложение перезапускалось в 11:42» — а не просто «нет связи» | демо `health`: 18/18 — урезанный CPU, блокировка базы, `kill -9` приложения, всё возвращено |
| Упала служба уведомлений | обслуживание не останавливается; предохранитель размыкается, письма копятся в очереди недоставленных и досылаются после восстановления | демо `notify-down`: 8/8 — предохранитель разомкнулся, после восстановления новые письма доставляются, 100 писем из очереди недоставленных доставлены повтором, предохранитель замкнут |
| Переустановили ПК отделения, потеряно хранилище брокера | новые события доходят в центр с первого | тест `RegionStreamRecreatedIT`; стенд: все события пересозданного потока b01 в центре |
| Центру не хватило памяти | центр завершается и сам поднимается, отделения работают; дамп памяти сохраняется для разбора | конфигурация стенда (ДД §11.7) |
| Много клиентов одновременно | ни дублей, ни потерь | тест `ConcurrentIssueIT`: 20 одновременных повторов одного запроса → один талон; 100 параллельных выдач → уникальные номера |
| Нет ML-модели | работает статистика, затем значение по умолчанию | тест `DurationModelChainIT` |

**Мониторинг отделений** идёт по тому же каналу, что и события, без отдельного агента и удалённого доступа:

- **метрики ПК и приложения** (CPU, память, база, диск, скорость своего API, качество связи) приходят каждые 10 с;
  центр хранит их 48 часов и строит графики в Grafana;
- **правила** превращают метрики в понятные фразы в обзоре сети: «ПК отделения не справляется», «на диске осталось
  7 %», «часы отделения расходятся с центром»; правила меняются в файле без пересборки;
- **важные логи** (ошибки, предупреждения, старт и остановка) отделение отправляет само; при обрыве они ждут на его
  диске и доезжают со своим временем;
- **полные логи за полчаса и снимок диагностики** (что делают потоки, кто кого блокирует в базе, связь) — по кнопке в
  карточке отделения; снимок приходит даже при зависшей базе;
- **сам центр** тоже под наблюдением: метрики в Prometheus, дашборд «ЕСУО · Центр», строка «Центр» в обзоре сети.

Честно о пределах: база отделения не реплицируется, резервная копия — ручной дамп (`scripts/backup`). Для хакатона
это сознательный выбор; путь к продуктиву описан в ДД §18.

Подробнее — ДД §11, §13.

## 6. Покрытие требований

### Десять обязательных проверок

Автотесты: **343 теста узла, 222 теста центра, 14 тестов роя, 42 теста модели, 8 тестов пульта сценариев, 0 падений**
(`./mvnw -pl node-app -am test`, `./mvnw -pl center-app -am test`, `uv run pytest`) и тесты экранов на телефоне и
десктопе (Playwright). Демо-сценарии — проигрыш рабочего дня на поднятом стенде с проверками по ходу.

### Сверх обязательного

| Фича | Зачем бизнесу |
|---|---|
| **Автономное отделение и подключение без настройки центра** | сеть растёт без работы в центре; обрыв связи не останавливает приём; до недели офлайн без потери данных |
| **Планирование нагрузки и квота записи** | отделение не принимает больше записи, чем сможет обслужить; руководитель узнаёт о нехватке окон до очереди, а не после |
| **Прогноз длительности (ML + каскад)** | правильное число окон по часам: в пенсионный день ожидание 3,9 минуты вместо 94; на стенде — очередь 16 вместо 72 (`pension-ab`) |
| **Честное ожидание** | интервал вместо одной цифры; «нет данных» вместо выдуманного числа |
| **Журнал решений** | любой вызов и любое закрытие записи объяснимы задним числом |
| **Мониторинг и диагностика отделений** | проблему ПК видно в центре раньше, чем позвонит отделение; логи и снимок — без выезда и удалённого доступа (`monitoring` 17/17, `health` 18/18) |
| **250 000 отделений на одном центре** | проверено роем на ноутбуке: без потерь событий, без перезапусков центра, обзор сети открывается мгновенно |
| **Обзор большой сети** | сводка, регионы, худшие отделения, поиск и фильтры; аномалии: нет связи, нет открытых окон, растут просрочки, завис обмен, перегрузка дольше 15 минут, правила не применились, база не отвечает, правила мониторинга |
| **QR без интернета и без подделки** | QR на табло сам переключается на Wi-Fi отделения при обрыве связи; код меняется каждые 2 минуты — разосланное фото не работает; наклейку можно отозвать |

| **Воспроизводимые демо-сценарии и пульт** | 11 сценариев, одинаковая «подпись хода событий» в повторных прогонах; запуск кнопкой на демо-странице |

## 7. Интерфейсы

Шесть экранов в одной сборке, раздаются самим отделением и центром, плюс дашборды Grafana:

- **Клиент** — поиск отделения, запись, QR-талон, живой статус с интервалом ожидания, отмена, перенос; при вызове —
  полноэкранное «Вас вызывают» со звуком и вибрацией; после потери сети сам переподключается и продолжает с тем же
  талоном.
- **Табло** — вызовы со звуком и QR для входа в очередь.
- **АРМ оператора** — окно, услуги, «Следующий», перенаправление, возврат, неявка, клиент без талона, инцидент;
  источник талона (запись / QR / живая очередь) виден сразу.
- **Кабинет руководителя** — очередь, аналитика, нагрузка по часам с уровнем и причинами, рекомендации, справочники,
  правила, инциденты, карточка модели, печать QR-наклейки.
- **Обзор сети** (центр) — сводка, регионы, худшие отделения, поиск; карточка отделения со строкой «Узел» (здоровье
  ПК), кнопками «Подробные логи» и «Снять диагностику» и ссылкой на графики; строка «Центр»; правила и версии,
  уведомления.
- **Демо-пульт** — журнал решений человеческим языком, демо-часы, связь с центром, запуск демо-сценариев кнопкой с
  живым логом.
- **Grafana** — дашборды отделения, сети и центра, логи отделений.

На всех экранах — режим «крупный шрифт и высокий контраст» и тёмная тема.

## 8. Как проверить самостоятельно

```bash
cp .env.example .env              # задать DB_PASSWORD, JWT_SECRET, LEAF_PASSWORD, MP_WEBHOOK_SECRET, CENTER_ADMIN_PASSWORD
docker compose --profile monitoring up -d --build   # центр + два отделения + все экраны + мониторинг
./scripts/demo/run.sh doctor      # проверка стенда: всё зелёное — можно смотреть
./scripts/demo/run.sh pension-ab  # главное демо: прогноз против его отсутствия (~4 мин)
./scripts/demo/run.sh health      # хаос на ПК отделения: центр видит, что именно сломалось
./scripts/demo/run.sh list        # все одиннадцать сценариев
./scripts/demo/run.sh repeat normal-day 3   # три прогона, подписи должны совпасть
```
