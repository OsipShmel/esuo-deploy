# Шпаргалка: демо A/B «прогноз против его отсутствия»

Один прогон — одно видео. Два отделения, одна и та же трасса клиентов пенсионного дня (на 30 % больше клиентов,
чем в профиле), разница только в знаниях:

| | b01 — без прогноза | b02 — с прогнозом |
|---|---|---|
| История | нет | шесть недель (`history.sql`) |
| Модель длительности | выключена | `dm-demo-01` |
| Во что упирается прогноз | константа 300 с | коэффициенты модели |

Правило, которое создаёт разницу: **руководитель утром ставит смену по прогнозу своего отделения**
(`⌈работа часа / (60 × 0,85)⌉` окон, максимум 5 — столько окон в отделении).

## Перед записью

```bash
# .env: DEMO_MODE=true, затем пересоздать ноды
docker compose up -d --build
./scripts/demo/run.sh pension-ab                 # сам готовит стенд (≈30 с) и играет день
./scripts/demo/run.sh pension-ab --rate 120      # быстрее; для видео подходит любая скорость
./scripts/demo/run.sh pension-ab --from 09:00 --to 11:00   # только отрезок дня
AB_SKIP_PREPARE=1 ./scripts/demo/run.sh pension-ab         # без повторной подготовки (стенд уже готов)
```

Длина дня 08:50–12:30 на экране: ×60 — 3 мин 40 с, ×120 — 1 мин 50 с, ×180 — 1 мин 15 с. Утро перед днём
(прогноз, запись, МП) идёт в реальном времени, ≈20 с с паузами (`--pace` — длина паузы).

Открыть заранее (вкладки браузера):

1. центр `:8081/network` — плитки b01 и b02 рядом;
2. табло b01 `:8080/board` и табло b02 `:8090/board` — рядом, в двух окнах;
3. админка b02 `:8090/admin` → «Нагрузка» и админка b01 `:8080/admin` → «Нагрузка»;
4. экран клиента b02 `:8090/` → «Записаться» (платежи, сегодня);
5. демо-пульт `:8080/demo` — журнал решений.

## Кадры по ходу прогона

| Шаг в терминале | Что показать | Что сказать |
|---|---|---|
| **2. Прогноз дня и смена** | Таблица в терминале; админка «Нагрузка» обеих нод, таблица «работа и мощность по часам» | «Одна и та же трасса. b01 думает, что в 09:00 придёт около 160 минут работы, b02 — почти вдвое больше. b01 ставит 4 окна утром и 2 к полудню, b02 — все 5.» |
| **3. Запись на сегодня** | Экран клиента b02: на 09:00–12:00 записаться нельзя, дальше — половина слотов; у b01 всё открыто или наполовину | «b02 заранее закрыло запись на часы, которые точно не вытянет. Людей в зале не выгоняем — закрываем только будущую запись.» |
| **4. МП записывает на 10:00 и 15:00** | Строки «подтверждена / отказ BOOKING_LIMITED» | Главный кадр: «b01 приняло запись в час, который уже перегружен. b02 отказало — и то же приложение предложит другое время. 15:00 спокойный — открыт у обоих.» |
| **5. День, 09:00–10:00** | Центр `/network`: плитки «Окна 4 из 5» и «5 из 5», «Ожидают», «Самое долгое ожидание»; табло | «Поток пошёл на 30 % выше плана — перегружены обе, это честно: у отделения всего 5 окон.» |
| **10:00–11:00** | Табло обеих нод: очередь b01 растёт быстрее; экран клиента b01 — честное ожидание перед выдачей талона | «Клиент в зале видит реальное ожидание до того, как взять талон.» |
| **11:00** | b01 по своей смене закрывает окно (3 окна) — очередь прыгает; админка b01: баннер «Откройте окно», причина «окон меньше, чем нужно» | «Система b01 видит проблему по факту, но смену уже не пересобрать: люди поставлены утром по неправильному прогнозу.» |
| **12:00–12:30** | Центр `/network`: «Ожидают» и «Самое долгое ожидание» у b01 примерно вдвое больше; аномалия «перегрузка»; пульт — журнал `load.level_changed` с причинами | «К полудню очередь b01 вдвое длиннее, и ждут там вдвое дольше.» |
| **6. Итоги** | Таблица в терминале (или `docs/demo/jury/ab-report.md`) | Среднее и максимальное ожидание, очередь к концу, запись на 10:00. |

## Если спросят

- **«Почему b02 тоже в перегрузке?»** Поток на 30 % выше плана, а окон в отделении пять. Прогноз не создаёт окна —
  он ставит в смену всех, кого нужно, заранее закрывает запись и честно говорит клиенту, сколько ждать.
- **«Почему b01 не открыл окно по рекомендации?»** Окно — это человек. Смену ставят утром, и b01 поставил её
  по константе 300 с. Рекомендация приходит, когда очередь уже есть.
- **«А простые средние дали бы то же?»** Почти да, если история есть: средние по истории отстают от предела точности
  на 2–3 %. Модель выигрывает на новом сотруднике и на отделении без истории — см. `docs/demo/ml-report.md`.
- **«Не подогнано?»** Длительность обслуживания в прогоне берётся из «правды мира» трассы, а не из модели;
  трасса, мир и модель воспроизводятся по зерну. `./scripts/demo/run.sh repeat pension-ab 3` — три прогона
  с одинаковой подписью (план смены, решения по записи, худший уровень каждого часа).
