# Как проверить решение: десять проверок ТЗ

Пошаговая проверка для тех, кто видит систему впервые. На всё — около 20 минут, большая часть автоматическая: демо-сценарий
сам создаёт клиентов, ведёт окна, печатает в терминале, что происходит и куда смотреть, и отмечает проверки ✔/✘.

## 0. Запуск (5 минут)

Нужны Docker, `curl`, `jq`, `python3` 3.9+.

```bash
cp .env.example .env              # впишите DB_PASSWORD, JWT_SECRET, LEAF_PASSWORD, MP_WEBHOOK_SECRET (любые строки)
docker compose up -d --build      # центр + отделения b01 и b02 + симуляторы мобильного приложения и уведомлений
./scripts/demo/run.sh doctor      # проверка стенда; первый старт нод — до минуты, при красном подождите и повторите
```

Экраны (логины `operator` / `admin`, пароли из `.env`, по умолчанию `operator123` / `admin123`):

| Экран | Адрес |
|---|---|
| Клиент | http://localhost:8080/ · через центр: http://localhost:8081/ |
| Табло | http://localhost:8080/board |
| Оператор | http://localhost:8080/operator |
| Руководитель | http://localhost:8080/admin |
| Обзор сети (центр) | http://localhost:8081/network — вход `network` / `CENTER_ADMIN_PASSWORD` из `.env` |

API центра, кроме публичного шлюза клиента, закрыт: для `curl` нужен токен оператора сети —
`TOKEN=$(curl -s -X POST localhost:8081/api/v1/auth/login -H 'Content-Type: application/json' -d '{"login":"network","password":"network123"}' | jq -r .access_token)`,
дальше `-H "Authorization: Bearer $TOKEN"`. Скрипты `scripts/` входят сами (`scripts/center-auth.sh`).
| Демо-пульт: журнал решений системы | http://localhost:8080/demo |

## 1. Десять проверок

| # | Проверка ТЗ | Как проверить на стенде | Что увидите | Автотест |
|---|---|---|---|---|
| 1 | Предварительная запись | `./scripts/demo/run.sh three-sources` и `./scripts/demo/run.sh mp`; вручную — клиентский экран → «Записаться» | запись через сайт центра и через мобильное приложение попадает в очередь отделения; МП получает ответ со ссылкой на статус; повтор вебхука не создаёт дубль | `AppointmentCreateIT`, `CheckInIT`, `MpTicketRpcIT`, `BookingQuotaIT` |
| 2 | Талон по QR | на табло `localhost:8080/board` — QR; откройте его ссылку в браузере того же компьютера (или `three-sources`). С телефона — если стенд развёрнут в локальной сети (README, «Две машины»), на одной машине порты слушают только localhost | выбор услуги → талон с номером, позицией и интервалом ожидания; статус обновляется сам | `QrIssueIT` |
| 3 | Вызов свободным окном | экран оператора → открыть окно → «Следующий» (или `normal-day`) | вызов появляется на табло со звуком; в демо-пульте — почему выбран именно этот клиент | `CallNextIT`, `AutoCallOnFreeIT` |
| 4 | Два окна без двойного назначения | `./scripts/demo/run.sh disputes` | два окна с общей услугой вызывают одновременно — каждое получает своего клиента | `ConcurrentCallNextIT` |
| 5 | Закрытие окна с активным клиентом | `disputes` | мягкое закрытие — клиента дообслуживают; принудительное — клиент возвращается в очередь на своё место | `CloseWindowIT` |
| 6 | Перенаправление | `disputes` | клиент переходит в другое окно или на другую услугу, принимающее окно берёт его первым | `RedirectIT` |
| 7 | Восстановление после перезапуска | выдайте и вызовите талон на экране оператора, затем `docker compose restart node-b01`, через минуту обновите экраны | очередь, вызванный клиент и занятое окно на месте; таймер повторного вызова продолжается | `RestartRecoveryIT` |
| 8 | Недоступны уведомления | `./scripts/demo/run.sh notify-down` (~4 мин, реальное время) | очередь работает; предохранитель размыкается, письма копятся в очереди недоставленных; после восстановления — досылаются | `NotificationOutageIT` |
| 9 | Конкурентное создание талонов | команда ниже | 20 одновременных запросов с одним ключом — один талон | `ConcurrentIssueIT` (плюс 100 параллельных выдач — уникальные номера) |
| 10 | Аналитика руководителя | `./scripts/demo/run.sh analytics`, затем `localhost:8080/admin` → «Аналитика» | сводка по источникам, услугам и окнам, загрузка окон, отклонения — за две недели истории | `AnalyticsSummaryIT` |

Проверка №9 на стенде — 20 одновременных запросов на талон по QR с одним `Idempotency-Key`:

```bash
for i in $(seq 20); do
  curl -s -X POST localhost:8080/api/v1/public/qr-tickets -H 'Content-Type: application/json' \
       -H 'Idempotency-Key: jury-check-9' \
       -d '{"qr_code":"demo:b01","service_id":"00000000-0000-4000-8000-000000000001","device_id":"jury","client_category":"default"}' &
done | jq -r .ticket_id | sort | uniq -c        # ожидается одна строка: «20 <один и тот же ticket_id>»
```

## 2. Сверх ТЗ: главное демо

```bash
./scripts/demo/run.sh pension-ab      # ~4 минуты; --rate 120 — вдвое быстрее
```

Один и тот же пенсионный день на двух отделениях: b01 без прогноза, b02 с моделью длительности. Смотрите обзор сети
`localhost:8081/network` и два табло рядом (`:8080/board`, `:8090/board`). В конце терминал печатает таблицу сравнения,
полный отчёт — `docs/demo/jury/ab-report.md`. Что показывать в какой момент — [шпаргалка](ab-cheatsheet.md).

Ещё два сценария про устойчивость и нагрузку:

| Сценарий | Что показывает |
|---|---|
| `./scripts/demo/run.sh link-cut` | обрыв связи отделения с центром посреди дня: зал работает, после восстановления события докачиваются |
| `./scripts/demo/run.sh pension-day` | пик пенсионного дня: очередь растёт, просрочки, рекомендация открыть окно |

После `pension-ab` стенд остаётся в «пенсионном дне»; вернуть обычный режим — `./scripts/demo/run.sh normal`.
